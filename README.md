# AOTG — AI-Optimized Toolchain Generator

**AOTGは、利用するコンピューターと作業目的に合わせた「最適化済みツール一式」を生成するための汎用ツールです。**

環境を調査し、改善案を作り、実測で比較したうえで、採用した構成を再現可能なキットとして出力する仕組みを目指しています。最初の用途はローカルLLMによるコーディング支援で、機材や推論ソフトウェアが異なる環境にも対応できる設計です。

## 何を生成するのか

AOTGは、対象の**機材・OS・ソフトウェア・用途・制約**を入力として扱います。

- **対象環境**：CPU、GPU、共有RAM／専用VRAM、ストレージ、OS、ドライバ、利用可能な計算基盤。
- **用途と評価条件**：使用モデル、入力長、推論・コード編集などの作業、目標とする速度、正確性、安全・資源制限。
- **最適化対象**：クライアント／コーディングエージェント、推論API、推論エンジン、モデル形式・量子化、GPUカーネル、Prefill／Decode、KV／Prefix／expertキャッシュ、CPU・GPU・SSD間の処理・データ配置など。
- **改良手段**：既存設定の調整から始め、計測で必要性が確認できた場合は、オープンソースのfork、限定パッチ、専用カーネルやツールの生成まで候補にする。

最終的には、固定したソフトウェア版・設定・必要な差分に加え、構築・起動・検証・停止・復帰の手順と測定根拠をまとめた**環境専用の実行キット**を生成します。モデルの重みや秘密鍵などは、キットに無断で同梱しません。

**「変更できるものをすべてforkする」こと自体は目標ではありません。** 設定だけで改善できればそれを採用し、コード変更が必要な箇所だけを改修します。AIは将来の最適化案やコード変更案の生成を支援し、採否は独立したテストと実測で判断する構成を目指します。

## 想定する処理の流れ

```text
対象PC・ソフトウェア・使用目的
             ↓
環境検出・互換性と制約の整理
             ↓
ベースライン計測・ボトルネックの特定
             ↓
最適化案の生成（設定 → 必要ならfork／patch／専用コード）
             ↓
隔離した環境でビルド・実測・独立検証
             ↓
品質と安全性を維持し、改善が再現した候補だけ採用
             ↓
再現・検証・復帰できる専用キットの生成
```

評価の中心は**同じ品質の仕事を終えるまでの時間**です。最大tok/sだけでなく、TTFT、Prefill、Decode、ツール往復、OpenCodeの全工程時間、RAM／VRAM、SSD I/O、温度などを区別します。量子化などで品質が変わる場合は「同品質の高速化」とは呼ばず、性能・メモリ・品質のトレードオフとして扱います。

改善が再現しなければ不採用として理由を記録します。**必ず速くなること、ハードウェアの能力上限を超えること、推論エンジンの変更だけでモデルの判断能力が向上することは約束しません。**

## 最初の用途と、現在できること

最初の検証対象は、ローカルの推論環境と開発用クライアントを組み合わせたコーディング支援です。推論エンジン、モデル、計算資源と利用条件は環境ごとにmanifestで指定します。

**現在の実装はMVP（合成データによるdry-run）です。**

| 機能 | 現在の状態 |
| --- | --- |
| 環境manifest／検証 | Linux・Windowsの合成fixtureとスキーマ検証に対応 |
| ローカル環境検出 | 実行先OSの許可された読み取り専用情報を一部取得 |
| 候補作成・計測・比較 | 合成データで試行し、判定と試行履歴を記録 |
| `build-kit`／`verify-kit` | **検証用のJSONメタデータ**を生成・照合。実機に適用するキットではない |
| 実機での自動チューニング | 未実装・未検証 |
| AIによるfork／GPUカーネル改修 | 将来の構想。現時点で自動生成できるとは主張しない |
| 本番への適用・自動復帰 | 未実装。実機変更の許可も与えない |

現行のOS検出では、推論エンジン・モデル・API・OpenCodeの設定までは自動収集しません。取得できない項目は不明として扱います。合成ベンチの数値は実機の高速化実績ではありません。

今後は、[UOB-50（実務ベンチ・独立評価）](https://linear.app/uobnnisiuk/issue/UOB-50)をはじめ、実機測定、有限な設定探索、必要に応じたsource改修、実行可能な専用キットの生成へ段階的に進めます。初回実装の詳細と受入条件は[MVP設計](docs/mvp.md)、[manifestスキーマ](schema/manifest.schema.json)、[基準ベンチのfixtureと測定設計](docs/benchmark.md)を参照してください。

## 安全と再現性

実機の計測やソフトウェア改修は、既存サービスとは分離した環境で行います。測定の開始条件・試行数・時間・資源上限を固定し、失敗や性能悪化も記録します。生成物の本番適用は独立した検証と明示的な許可を必要とします。

公開リポジトリに実機の構成値、認証情報、秘密鍵、内部アドレス、個人ファイル、非公開の業務コード、モデル重みを保存しません。実機用の構成には、元の版・変更差分・検証証拠・復帰手段を残します。

## Mock dry-run

Python 3.11以上で、リポジトリのルートから実行します。実行時の外部依存はありません。

```sh
python -m aotg inspect --manifest tests/fixtures/linux-mock.json
python -m aotg plan --manifest tests/fixtures/linux-mock.json --output out/plan.json
python -m aotg bench --plan out/plan.json --output out/run.json
python -m aotg compare --run out/run.json --output out/decision.json
python -m aotg build-kit --run out/run.json --decision out/decision.json --output out/kit.json
python -m aotg verify-kit --kit out/kit.json --run out/run.json
```

Windows側の例には `tests/fixtures/windows-mock.json` を使えます。中断時は同じplanと前回のレポートを `bench --resume <前回レポート>` に指定し、新しい出力先に結果を保存できます。出力先には、試行記録を保存できるAOTG専用ディレクトリを使ってください。既存の結果ファイルがある場合は、別の出力先を指定します。

ローカルOSの読み取り専用検出は、Linuxで `python -m aotg inspect --adapter linux`、Windowsで `python -m aotg inspect --adapter windows` を使います。取得できない項目は `null` で示します。推論エンジン・モデル・API・OpenCodeの設定は自動取得の対象外です。LinuxのROCm欄はインストール情報から取得します。WindowsのVRAM容量とGPUランタイムは未取得です。公開リポジトリの環境サンプルは合成データです。
