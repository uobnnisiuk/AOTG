# AOTG MVP 設計

[UOB-48](https://linear.app/uobnnisiuk/issue/UOB-48) の初回実装は、機材とモデルの条件を記述し、構成候補を有限の試行計画に変換し、独立した評価から再現用 kit を組み立てる。公開 fixture はLinux／Windowsの合成構成を使う。

## 設計上の判断

- Python 3.11 以上を採用する。Linux と Windows で同じデータモデルと CLI を使い、OS 固有の読取を adapter に閉じ込める。実行時は標準ライブラリを使用し、ネットワーク不要で dry-run とユニットテストを動かす。
- 機種名を条件分岐の起点にせず、manifest の OS、デバイス、利用可能なバックエンド、計測条件と保護条件を用いる。統合 GPU の共有予算と独立 GPU の専用 VRAM、実際のセッションでの消費量を別項目に置く。
- 既存の公開版と設定調整から候補を作る。構成で満たせない要件が実測で示された場合に、固定した上流コミットに対する fork・patch・kernel の候補を追加できる契約にする。初回 runner は baseline と設定候補を模擬する。

## コンポーネントの契約

| コンポーネント | 入力と出力 | 責務 |
| --- | --- | --- |
| 検出 adapter | 許可済み OS 情報 → manifest v1 | 許可リストの読取で OS／CPU／GPU／メモリを把握する。engine、モデル SHA、API とクライアントは公開済みの明示入力または匿名化済み証拠を利用する。取得不能は `null` として残し、推定で補完しない。 |
| Candidate | ID、種類、基準、固定版、狭い設定差分 | 変更点を機械可読データにする。将来の source 候補では上流コミットとパッチのハッシュ、ビルド条件を追加する。 |
| Planner | 検証済み manifest と seed → 試行順、候補一覧、上限 | 条件を満たす候補だけを並べ、同じ入力から同じ順序と識別子を得る。中断の再開では入力・計画・既存試行を照合する。 |
| Runner | 計画 → 試行ごとの計測データ、状態 | 初回は合成データ。将来は試行ごとに隔離した作業コピー、明示した実行先、待受、環境、終了と後片付けを管理する。失敗・時間切れ・保護停止も試行記録に残す。 |
| Judge | 固定計画と試行結果 → ゲート判定と根拠 | 速度と独立品質の判定を runner から分離する。テストは評価対象のワークスペースの外に置き、別環境で評価する。必要な値の欠測や異常は採用を保留する。 |
| Kit builder／verifier | 候補、差分、判定、結果 → kit と検証結果 | 根拠と版、適用条件、差分、復帰点を結び付ける。独立検証で証拠と kit の整合を確認し、配布や本番への適用は別工程にする。 |

manifest は schema version、採取方法、機材、OS、engine／model／API、client、測定条件と保護条件を持つ。実機用の版固定では engine と client の版に加え、モデル・draft pack・入力・独立テストのハッシュを照合する。モデル SHA は既存の検証結果を参照して大きな重みの再読み込みを避ける。実機向けの kit には生成元、対応条件、元構成の識別子、差分と逆方向の差分、再現手順、復帰後の認証・SSE・tool-call 確認を含める。検証が終わるまで適用工程に進めない。

## 計測、採否、停止

- 短文、長文、OpenCode の実作業を別の workload とする。TTFT、prefill・decode のトークン数と時間、tool の要求から結果受領まで、全作業の壁時計時間を個別に記録する。RAM/UMA、専用 VRAM、SSD 読み書き、swapout 増分、温度、異常停止も記録する。共有メモリの計測値は重複加算しない。
- 品質ゲートは独立ビルド・テスト、公開 API と設計の維持、正常な最終応答、認証／SSE／tool-call 回帰、長文診断の合格を要求する。介入や再修正も記録する。比較可能な反復の全件を集計し、速度向上ゼロも保存する。対象 workload の壁時計時間に、事前固定した最低改善幅を求める。他指標の劣化許容幅と資源しきい値は開始前に固定する。
- 初回の合成評価は baseline、same-settings、mock-batch の 3 候補に各 3 試行、既定 seed 42、1 回の bench 呼び出しに 5 秒の上限。出力一致・ツール呼出し・テストの合成品質フラグの通過、壁時計時間の中央値が 5% 以上改善、個別性能・資源指標の悪化が 5% 以内、温度上昇量が 2℃ 以内かつ 85℃ 以下を模擬候補の判定に使う。実機の採用や稼働判断には別途実測を要する。
- 実機実行を将来追加する場合は同時実行 1 件とし、試行数、各試行と全体の時間、出力トークン数、メモリ予算、SSD 使用量・空き容量、温度と冷却、swap、欠測時の扱いを対象機ごとに計画へ固定する。数値未確定の計画、資源競合、機器の誤選択、保護条件違反、タイムアウト、GPU／PCIe／I/O／OOM 異常では停止する。既存の保護値より厳しい方を適用する。中断時と再試行時にも上限、掃除、試行記録の整合を検証する。
- 実行時には AOTG 専用ディレクトリを指定して kit と試行記録を保存する。実機の既存サービス、API、認証・SSH・鍵・HOME、OS・ドライバ・BIOS・ネットワーク、業務用ゲートウェイ、OpenCode 本番設定、K8 の定期処理、Footprint、不可分研究、モデル重みは保護対象。公開リポジトリには秘密値・内部アドレス・非公開パス・業務コードを含めない。

## 初回受け入れと次工程

1. manifest v1 を 2 種の fixture で検証し、欠測、メモリ区分と provenance を確認する。実機を読取できない場合は fixture と未確認項目を記録する。
2. `inspect → plan → bench → compare → build-kit → verify-kit` を合成データで完走させる。同じ入力からの計画、改善ゼロの根拠、部分レポートからの再開と改変レポートの拒否、kit の整合検査を確認する。
3. ユニットテストと CI で Linux／Windows の主要経路を確認する。ベンチ fixture と計測条件を定義する。
4. 次の実装は [UOB-50](https://linear.app/uobnnisiuk/issue/UOB-50) のオフライン評価ハーネスで、固定の C++／C# 入力に対する独立判定と機械可読結果を接続する。実負荷計測は別ゲートとし、UOB-52〜56 は依存工程の完了後に進める。
