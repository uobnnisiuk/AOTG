# 基準ベンチの fixture と測定設計

[UOB-50](https://linear.app/uobnnisiuk/issue/UOB-50) の初回成果は、ベンチ入力の fixture と計測の設計。対象実機への負荷試験は未実施。

## 入力と採点

[`catalog.json`](../tests/fixtures/benchmark/catalog.json) は、固定の seed、サンプリング、ケースごとの出力上限、入力ファイルと期待値を記録する。小さな C++／C# の課題は AOTG 用に作った合成コードとベクトルで、履歴の課題とは別の ID を持つ。公開リポジトリ課題は Mono.Options のコミットとソース SHA-256 を指定する。上流のソースや過去の修正パッチは同梱していない。

- 短文と生成ツールの疎通は固定入力を使い、認証失敗、JSON、SSE 終了、tool-call、ツール結果に基づく最終回答を別々に評価する。tool fixture は模擬 tool の入力と期待値を指定する。
- C++ は半開区間の隣接・負値・逆順入力・無効区間を、C# はバッチ内／登録済みとの重複、一括処理の原子性、失敗後に再登録できることを判定する。実ベンチでは starter と課題文だけを候補に渡し、採点ベクトルは評価側で保持する。
- 公開 C# リポジトリ課題は最初に固定版で不具合を再現し、独立テストの正例と負例を照合する。評価の前にビルド入力・ツールチェーンとテストのハッシュを記録する。公開版の添付物を取得できない場合は欠測として扱う。

## 実測 runner の計画

1. 既存証拠を照合し、同条件で欠けている指標を特定する。モデル・draft pack・エンジン・クライアント・コード・独立テスト・コマンド、コンテキスト、入力／出力のトークン数、sampling、seed、ツール構成を固定する。容量診断では設定上限と実入力長を分けて記録する。
2. 一度に変える要素を 1 つに限定する。同じ cache 条件ごとに短文・小課題を baseline と候補で各 3 回まで、全組の開始順は A-B、B-A、A-B の順にする。cold／warm は別群にし、キャッシュ済み入力トークン、ウォームアップと冷却、ワークスペース初期化、失敗と中断を記録する。
3. 要求送信から最初の有効出力までを TTFT とする。エンジンの prefill と decode はトークン数・時間・速度を採取し、draft 採択率は採択数と試行数を保持する。tool-call から結果受領を tool roundtrip とし、全工程はセットアップと冷却・待ち・編集・ビルド・テスト・介入・最終応答・独立採点までを計測する。ツール実行時間の和と、往復や全体の壁時計時間は別に測る。
4. MemAvailable と RSS、共有メモリの GPU 使用、専用 VRAM、SSD の読取・書込バイト数、GPU/NVMe 温度、swapout 増分と GPU／PCIe／I/O／OOM の異常を記録する。サンプラーの間隔・負荷と試験準備、計測器の有無で比較した負担も保存する。時刻やピークの取得窓を明記する。
5. 全件と中央値、範囲、欠測理由、独立テストの成否、介入、最終応答の有無、ゲート判定を機械可読結果に記録する。上限・前提・復帰が確認できない実負荷は開始せず、実行中の保護異常は即時停止する。保護停止も母数に含め、同じ workload を正常完遂した時間のみを時間比の対象にする。

次は fixture と独立検証器をオフラインで接続し、失敗・欠測・time-out の出力と集計を固定する。
