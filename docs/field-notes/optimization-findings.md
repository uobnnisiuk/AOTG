# 最適化の知見

## O-001: decode速度は実作業時間の代替指標にならない

- 問題: 最速tok/sの構成をコーディング用に採用できるか。
- 根拠: 既存 [UOB-27](https://linear.app/uobnnisiuk/issue/UOB-27) の同一FlashNext IQ3_S比較。R9700/MTPは短文decodeが速かったが、C++総時間は8060S/DFlash2より長く、長文とC#はswap保護で中止。
- 結論: 初号機は既存8060S構成を出発点とする。R9700の再探索は後続。これはハードウェア一般の優劣ではなく、当該モデル配置と先読み方式を含む構成比較。
- 再現条件・数値: [履歴台帳](../../tests/fixtures/benchmark/historical-evidence.json)。2026-11-15の新規推論測定ではない。
- 未検証: より小さいモデル、別のGPU配置、同一先読み方式での結果。

## O-002: 冷温キャッシュと試行順を比較条件に含める

- 問題: 過去の短文TTFTの差が設定差か、キャッシュ再利用か。
- 事実: UOB-23の短文は再利用0、UOB-26の導入確認は0／115／115入力トークン再利用。これらを同じcold群として比較できない。
- 実装: 固定ABBA順とcache cohortをplanに含める。入力・品質テスト・profile・model/quant/sampling identityのhashをtrialに結び付ける。
- 未検証: 当該実機での新たな順序効果とばらつき。ハッシュ一致だけでは実際のキャッシュ状態を証明できないため、エンジンの再利用量の観測が必要。

## O-003: prefill候補は仮説として固定してから測る

- 仮説: 既存prefillに対する小／大バッチで、入力処理時間と冷却待ちの合計が変化する可能性がある。
- 比較案: 同じモデル、量子化、コンテキスト、KV、DFlash2、sampling、課題で、prefillのみを変更する2候補。値と上限は実行前の固定planで決める。
- 現在の確からしさ: **未測定**。改善を予告しない。短い編集課題ではtool往復や生成が支配し、prefill差が総時間に現れない可能性もある。
- 採用: 独立品質に合格し、順序を反転しても総作業時間の改善を再現した場合のみ。欠測は探索未完、全試行完了後の改善不成立は現状維持と区別する。
