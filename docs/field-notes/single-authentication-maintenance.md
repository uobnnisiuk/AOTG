# 単一認証から無人測定・復帰へ進むための記録

記録日: 2026-11-16。対象は既存のEVO-X3／K8 Plus初号機。[認証後の連携期限切れ](failures-and-limitations.md#f-012-対話認証後の短い期限に会話の待ち時間を入れない)から得た運用上の知見を保存する。**認証の準備と、本番停止・測定開始の許可は別である。** この文書は実行許可や初号機の完了報告ではない。

## 調査した問題と仮説

旧経路では対話認証の直後に90秒の機械間連携期限が始まった。認証、クライアントの準備、通知を会話の進行に合わせると、所有者がその場で対応し続ける必要があった。実際に期限切れで本番変更前に停止した記録がある。認証画面を開き直す運用は、所有者が常時画面の前にいるという誤った前提を残す。

仮説は、認証済みの権限を一つの固定済み計画に限定して期限付きで待機させ、開始許可と短い機械間連携を後段へ分ければ、入力後の所有者の立会いを不要にできる、というもの。待機期間を長くすることと、実際の90秒連携期限を延ばすことは区別する。

## 実装した専用経路

認証時には、内容を固定した制御コードのroot所有スナップショットと、一時的なsystemdサービスを作る。認証待機は単調時計で最大12時間、サービス全体は13時間で制限し、自動再起動しない。待機だけでは本番停止、モデル推論、既存の保守処理、復帰タイマーの作成を行わない。パスワード保存やsudoers変更も行わない。

開始には、所有者から別途得た明示許可を記録した、一度限りの開始指示が必要である。実行できるのは固定済みのowner-entryと認可計画だけで、任意のコマンドや別計画を渡す機能はない。開始指示は運用担当による承認の記録であり、人間の同意を暗号学的に証明するものではない。

手順は次の順序にする。

1. 所有者の都合のよい時に一度だけ認証する。入力を始める前の待ち時間をsudoの入力期限へ入れない。
2. 実際のサービスがactive/runningで、MainPIDと待機イベントのPIDが一致し、未消費・未終了であることを確認する。その確認後にSSHを閉じられる。過去のイベントだけから現在の待機を推定しない。
3. 別途、測定開始の明示許可を得て、実機状態・固定入力・残り待機時間を再確認する。K8側の連携処理を先に待受状態にし、その実状態を確認してから一度限りの開始指示を渡す。
4. 待機側が固定入力・期限・取消・開始指示の鮮度を再検査し、排他的な消費記録を保存して既存owner-entryへ進む。この時点から従来の90秒の機械間連携が始まる。
5. 以後の測定・復帰は既存の有限計画と独立した復帰制御に従う。追加のパスワード入力や所有者の立会いを手順に挟まない設計である。

期限切れ、取消、失敗した認証を自動再試行しない。既存の状態と保存記録を確認し、同じ消費済み記録を再利用しない。測定開始後に待機サービスを停止することを、既存の復帰手段の代用にしない。12時間／13時間は待機・サービスの上限で、測定や復帰の成功保証ではない。

## 独立確認で見つかった落とし穴

| 問題 | 修正と検証 |
| --- | --- |
| 読み取りプレビューでも動的なmodule loaderがコードを実行する | 元のloaderへ渡す前に、認可計画のcanonical hashが固定値に一致することを必須化。不一致ではloader本体を呼ばない負例を追加した |
| 初期の待機イベントが残っていても、現在のサービスは終了している場合がある | active/running、MainPID一致、未消費、後続イベントなしを確認する。inactive、PID不一致、終了・消費済みを拒否する |
| 検証やイベント保存の間に期限・指示鮮度・取消状態が変わる | 検証後、消費記録後、開始イベント出力後にも条件を確認し、固定処理の呼出し直前まで拒否できるようにした |
| 認証成功を、測定開始や復帰成功と取り違える | 認証待機、開始指示の消費、owner-entry結果を別々に記録する。終了コードだけで品質やGoalを完了にしない |

## 検証結果と未検証事項

既存Pythonによる40件のオフライン試験が成功した。実際の一時ディレクトリとdirfd操作を用い、owner処理、時刻、root所有属性、サービス応答は模擬した。固定入力の変化、再利用、不正なファイル、期限切れ、取消、古い開始指示、待機状態の不一致、module loader実行前の拒否を検査している。別担当のソースレビューも完了した。

記録時点の読み取り確認（2026-11-15 23:27:57 UTC）では、実機の認証待機サービスはまだ観測されず、開始指示も作成されていなかった。準備コードの配置・読み取り確認と、一つの認証画面の起動までを観測した段階である。実際の認証成立、SSH切断後の待機継続、12時間の期限動作、無人の測定・復帰は未実証。本番停止・新しい測定開始は未承認のままで、今回の準備から性能値や品質合格は得られていない。

## この環境固有の事情と今後の確認

既存SSH、Linuxの一時サービス、専用のowner-entry、K8の準備完了通知を利用している。他機種や任意の管理コマンドへ権限を一般化していない。応用可能な知見は、人間の入力時機と短い機械間期限を分離し、状態と許可の範囲を明示することである。

今後は実認証後の待機・切断継続を確認し、別途開始許可を得た時にだけ、先行待受から測定・復帰までを実証する。実際の状態と結果を追記するまで、[UOB-50](https://linear.app/uobnnisiuk/issue/UOB-50)／[UOB-53](https://linear.app/uobnnisiuk/issue/UOB-53)と初号機Goalの未完了条件は変わらない。
