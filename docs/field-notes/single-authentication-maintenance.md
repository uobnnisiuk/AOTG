# 単一認証から無人測定・復帰へ進むための記録

記録日: 2026-11-16。対象は既存のEVO-X3／K8 Plus初号機。[認証後の連携期限切れ](failures-and-limitations.md#f-012-対話認証後の短い期限に会話の待ち時間を入れない)から得た運用上の知見を保存する。**認証の準備と、本番停止・測定開始の許可は別である。** この文書は実行許可や初号機の完了報告ではない。

## 調査した問題と仮説

旧経路では対話認証の直後に90秒の機械間連携期限が始まった。認証、クライアントの準備、通知を会話の進行に合わせると、所有者がその場で対応し続ける必要があった。実際に期限切れで本番変更前に停止した記録がある。認証画面を開き直す運用は、所有者が常時画面の前にいるという誤った前提を残す。

仮説は、認証済みの権限を一つの固定済み計画に限定して期限付きで待機させ、開始許可と短い機械間連携を後段へ分ければ、入力後の所有者の立会いを不要にできる、というもの。待機期間を長くすることと、実際の90秒連携期限を延ばすことは区別する。

## 実装した専用経路

認証時には、内容を固定した制御コードのroot所有スナップショットと、一時的なsystemdサービスを作る。認証待機は単調時計で最大12時間、サービス全体は13時間で制限し、自動再起動しない。待機だけでは本番停止、モデル推論、既存の保守処理、復帰タイマーの作成を行わない。パスワード保存やsudoers変更も行わない。

開始には、所有者から別途得た明示許可を記録した、一度限りの開始指示が必要である。実行できるのは固定済みのowner-entryと認可計画だけで、任意のコマンドや別計画を渡す機能はない。開始指示は運用担当による承認の記録であり、人間の同意を暗号学的に証明するものではない。

手順は次の順序にする。

1. 所有者の都合のよい時に一度だけ認証する。入力を始める前の待ち時間をsudoの入力期限へ入れない。
2. 実際のサービスがactive/runningで、MainPIDと待機イベントのPIDが一致し、未消費・未終了であることを確認する。その確認後にSSHを閉じられる。過去のイベントだけから現在の待機を推定しない。
3. 別途、測定開始の明示許可を得て、実機状態・固定入力・残り待機時間を再確認する。K8側の連携処理を先に待受状態にし、その実状態を確認してから一度限りの開始指示を渡す。
4. 待機側が固定入力・期限・取消・開始指示の鮮度を再検査し、排他的な消費記録を保存して既存owner-entryへ進む。この時点から従来の90秒の機械間連携が始まる。
5. 以後の測定・復帰は既存の有限計画と独立した復帰制御に従う。追加のパスワード入力や所有者の立会いを手順に挟まない設計である。

期限切れ、取消、失敗した認証を自動再試行しない。既存の状態と保存記録を確認し、同じ消費済み記録を再利用しない。測定開始後に待機サービスを停止することを、既存の復帰手段の代用にしない。12時間／13時間は待機・サービスの上限で、測定や復帰の成功保証ではない。

## この環境固有の事情と今後の確認

既存SSH、Linuxの一時サービス、専用のowner-entry、K8の準備完了通知を利用している。他機種や任意の管理コマンドへ権限を一般化していない。応用可能な知見は、人間の入力時機と短い機械間期限を分離し、状態と許可の範囲を明示することである。

認証後の待機・切断継続と、別途開始許可を得てからの測定・復帰は、それぞれ実証する必要がある。認証待機の結果だけでは、[UOB-50](https://linear.app/uobnnisiuk/issue/UOB-50)／[UOB-53](https://linear.app/uobnnisiuk/issue/UOB-53)と初号機Goalの未完了条件は変わらない。

## 2026-11-16追補: Windowsの実際の引数受渡しを検証していなかった

最初の実認証試行では、所有者がsudoの入力を終えた後、リモートPythonの `-c` へ渡した起動用コードが `SyntaxError` で停止した。rootの認証待機サービスは作成されなかった。01:37:44 UTCの読み取り確認でも、待機サービスはnot-found、イベントと開始指示はなく、保護対象19ファイルと隔離配置した9入力のhashは不変、本番の既存プロセスと設定は維持されていた。認証入力の完了を、待機登録の成功と扱ってはいけない。

原因は、Windows PowerShell 5からネイティブSSHへ引数を渡す段階で、入れ子の引用符が失われることだった。以前の40件の模擬試験、PowerShell構文解析、POSIX側の引数分解検査は、この実際のWindows受渡しを通していなかった。論理上正しい起動文字列が、別プロセスへ同じbytesで渡るとは限らない。

独立したネイティブ引数記録器による比較では、Windows PowerShell 5.1.26100.9818で旧形式は期待638 bytesに対して受信606 bytesで不一致、新形式は期待・受信とも1137 bytesで一致した。旧形式では32個の二重引用符だけが欠落していた。この比較はSSHもリモートコードも実行せず、Windowsの引数境界だけを確認したものだ。受信した旧文字列をPOSIX引数分解のモデルとPythonのcompileだけで検査すると構文エラーとなり、新形式と復元したコードは構文検査を通った。この追加検査は実リモートシェルの実行ではない。

修正は起動用コードの伝送表現に限定した。元の535 bytesを引用符を含まない数値式から復元し、シェルが扱う括弧をescapeする。復元後の内容hashと元のbytesの一致を確認した。固定した待機制御コード、認可計画、開始前検査は変更していない。数値化は暗号化ではなく、起動文字列には内部情報が含まれるため、実値や生のコマンドは公開しない。

別の実経路検査（01:36:29 UTC）では、Windows PowerShell 5から既存のネイティブSSH・端末割当を経由してEVOのPythonへ渡した。通常プレビュー用の変形は終了コード0。実際の登録用起動コードそのものをsudoなしで渡す負例は、内容hash確認・compile・mainへの到達後、`Root isolated Python required` で終了コード1となった。構文エラーではなく、期待した権限拒否である。この検査は新しいrootサービスを作成せず、sudoもモデル推論も実行していない。

非対話のsudo確認も認証を要求して終了したため、利用可能な認証キャッシュがあるとは扱えなかった。修復後の登録には所有者の再入力が必要になった。これは失敗した準備が所有者へ追加負担を生んだ記録であり、自動的に認証画面を再表示し続けてよいという判断ではない。

この修復検査を終えた時点では、成功した特権付き登録、SSH切断後の待機、無人測定・復帰は引き続き未実証だった。本番停止・測定開始の別承認も得ていない。先の40試験は制御ロジックに関する証拠として残し、実際のネイティブ引数経路を含む成功証拠へ拡張解釈しない。
